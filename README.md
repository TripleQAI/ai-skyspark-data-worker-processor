# SkySpark data worker processor

This repository is being implemented in phases from `docs/skyspark-ingestion-implementation-plan.md`. The current slice provides strict configuration contracts, deterministic bounded planning, a PostgreSQL control schema and transactional repository, recoverable dispatch and publication outboxes, bounded stale-job recovery, a bounded concurrent worker, checksum-pinned Python script execution, bounded S3 raw/JSONL writers, a TimescaleDB history batch writer, contiguous site checkpoints, read-only metadata export inspection, EventBridge Scheduler definition generation, a fail-closed scheduled planner backed by versioned S3 configuration and inventory receipts, read-only run coverage, Lambda entrypoints, a Step Functions Standard definition, and persistent dispatcher, publisher, and recovery services. It does not yet include production SkySpark readers, a live LocalStack queue test, or a deployed AWS schedule.

The three scripts under `orginal-scripts/` are read-only references. The production adapter will be new code under `src/ingestion/adapters/skyspark/` after the source-query contract is verified. No source credential belongs in this repository. The generic script runner accepts only an approved manifest path and SHA-256 digest; it sends a job and source references over stdin and expects a `JobCompletion` JSON response. The checked-in default plugin manifest has no executable scripts yet.

## Phase 0 source proof

`scripts/inspect_phase0_exports.py` reports source CSV shapes and cross-reference counts without printing source IDs or row values. `local/fixtures/phase0/` contains invented replacement rows for all four supplied export shapes. `scripts/secret_preflight.py --root .` reports likely credential locations without printing values. Run it before an image build or future commit.

`skyspark-source-probe` is a separate read-only pilot command. Its default is a network-free dry run against approved binding and scope files. The configured SkySpark root is `http://44.221.91.30:8888/api/`; the approved site URI is appended from the binding. Real execution requires an approved pilot site and an AWS Secrets Manager secret. It does not mark data certified. See `docs/source-contract-status.md` for the exact gate and example commands. The probe does not use the legacy connector's embedded credential.

## Reviewed script contract

An approved reader can declare an `execution` block in the plugin manifest with a relative `.py` path, exact file SHA-256, timeout, maximum stdout/stderr bytes, and explicit environment variable names. The worker runs the file with an argument list, isolated Python startup, bounded output, and no shell command. `tests/fixtures/script_manifest.yaml` and `tests/fixtures/approved_script.py` demonstrate the contract with synthetic output only. A real script must write its raw evidence and configured target data before returning a completion record; production SkySpark scripts and feed-specific validators are still pending.

Each reviewed script declares `source_call_slots`, the maximum number of simultaneous SkySpark calls it may make. A PostgreSQL permit pool reserves that many fenced slots across worker tasks for the entire script invocation. The worker renews the reservation and terminates a subprocess if its lease is lost. The first plan pins the project capacity from `source_policy.max_concurrent_calls`; changing that limit later requires a coordinated drain and budget update before planning with a new profile.

## Storage slice

`S3RawStore` writes immutable, size-capped raw objects and source-scope manifests. `S3JsonlSink` writes bounded JSONL candidate batches. The worker verifies the physical S3 checksums, lengths, manifests, and row count before control certification. `TimescaleHistorySink` accepts typed point observations within the requested five-minute window, bulk loads a temporary table, merges idempotently, and commits a target receipt in one transaction. The worker verifies the raw S3 object plus that Timescale receipt. Feed-specific source completeness and row validation remain required before a production run. The initial JSONL layout is a testable sink format; columnar layout and retention need measurement in the pilot.

## Window checkpoint slice

History and rules each have a checkpoint per tenant, project, and site. An operator sets the approved starting cursor once with `seed-checkpoint`; reconciliation never invents one. When the final partition for a site's window (including an empty-scope job) is certified, certification, cursor advance, site completion, and one pending publication intent per job commit together if the window begins at that cursor. A later window waits for the earlier one; `reconcile-run` recovers it after the gap closes. Metadata creates publication intents for its certified site snapshots without a time-window checkpoint.

`publish-once` claims pending intents, checks the configured EventBridge bus exists, and sends batches of up to ten reference events. It records each accepted event ID and retries failed entries with backoff. `publication-service` runs that bounded operation continuously under ECS, sleeping at the configured interval when there is no full batch. A crash after EventBridge accepts an event can cause a resend; consumers must deduplicate by `publication_id`. `delivered` means EventBridge accepted the event, not that any downstream consumer processed it. A downstream rule or target is later work.

## Metadata export inspection

`inspect-metadata-export` reads the original equipment and point CSV format without changing the files. It checks project and site scope, duplicate IDs, equipment links, and the configured `his` marker values, then reports accepted equipment, points, historized points, site-level points, and every exclusion class. It never emits a `CertifiedInventory`: CSV exports do not prove that a SkySpark query returned a complete site snapshot. See `docs/metadata-export-inspection.md` for the read-only assessment of the supplied `1001` exports.

## Stale-job recovery

`recover-stale` moves a bounded set of sent but unfinished job references back into the dispatch outbox. It selects only expired running leases after a configured grace period or jobs with no recorded attempt after a longer configured delay. Active leases, certified jobs, and planned jobs with handled failures are excluded. A per-job redrive cap prevents repeated automatic requeue. `recovery-service` repeats this scan, and `dispatch-service` sends restored references in SQS batches of up to ten with per-entry retry. An old SQS message may also arrive; fenced job leases and idempotent job IDs handle duplicate delivery.

## Schedule definition slice

`skyspark-schedules` derives one EventBridge Scheduler definition per feed from an approved profile and binding. The default profile produces UTC-aligned history every five minutes, rules daily at 02:00, and metadata Sundays at 03:00. A schedule input contains the project and feed, a config hash and version-pinned S3 config reference, and Scheduler's due-time placeholder. It contains no endpoint, credentials, or site list. Preview is read-only and needs no database or AWS connection. `reconcile` also reads by default; `reconcile --apply` creates missing definitions and updates only definitions carrying the project's ownership marker. It preserves unrelated optional AWS schedule fields, refuses an unexpected target shape, and stops before mutation if it finds a colliding unmanaged schedule. It never deletes schedules.

All schedules default to `DISABLED`. `--enable` produces enabled definitions only when explicitly supplied. The schedule group, Step Functions Standard state machine, execution role, shared Scheduler delivery DLQ, and versioned config object must exist before enabling a schedule. Terraform describes some of these resources, but none has been applied or exercised in AWS. EventBridge Scheduler can deliver within the scheduled minute even with its flexible window off, so the planner must use the `scheduled_at` payload for deterministic window IDs.

The scheduled ingress code loads exactly the `versionId` named in `config_ref`, enforces the configured byte cap, rejects duplicate JSON keys, and validates a bundle shaped as `{"schema_version":1,"profile":{...},"binding":{...},"manifest":{...}}`. The resulting hash must equal the schedule input hash. `ScheduledTrigger` then checks project, tenant, profile, feed, and UTC due time before planning. History uses the previous configured interval; rules use the previous daily or weekly due time; metadata has no history window.

`persist-scheduled` reads the small trigger from `--trigger-file` or `SCHEDULED_TRIGGER_JSON`, resolves the pinned S3 config, and saves the deterministic run, jobs, and dispatch intents. The CLI and `ingestion.aws_handlers.plan_handler` share that planning function. History and rules select a project-scoped inventory receipt whose source is a completed metadata run, whose certification precedes the due time, and whose age is within `inventory_artifacts.max_age_hours`. A database pin keeps retries on the same inventory version. The S3 reader verifies that exact object version, receipt length and SHA-256, inventory identity, and all approved sites before planning. The full inventory stays in S3; only its receipt and schedule pin live in PostgreSQL.

The Phase 4 metadata reader accepts only complete, snapshot-consistent equipment and point pages, preserves Haystack tags and links, and rejects missing references or source caps. A reviewed local script reads the bounded HTTP fixture; the observed live SkySpark grids have no completeness receipt and therefore fail closed. After all site jobs certify, `publish-metadata-inventory` or the metadata-only workflow Lambda verifies their S3 evidence, rejects missing sites and unexplained scope shrinkage, writes an exact-version S3 inventory, and records adds/changes in PostgreSQL. The history/rules planner pins that version. The data provider must establish production page/completeness and deletion semantics before live metadata can publish. Terraform now describes ECS task wiring and IAM, but live Scheduler delivery remains in Phase 9.

`run-status` derives the state of one scoped run from job certifications and per-site completions. It reports `pending` while coverage can still finish, `certified` only when every job has evidence and every site is complete, `partial` when some sites complete before a terminal job or deadline, and `blocked` when none complete or the control record is inconsistent. Deadlines and poll cadence are in `resources.yaml`. The query is read-only; it does not stop workers or change a late run. The generated Standard workflow polls this status and terminates on certified, partial, or blocked coverage; a worker may still certify a late run after its workflow deadline.

`skyspark-workflow` prints the Step Functions definition from reviewed resources and three supplied Lambda ARNs without contacting AWS. The state machine invokes `ingestion.aws_handlers.plan_handler`, waits `workflow.poll_seconds`, calls `ingestion.aws_handlers.status_handler` with the run scope returned by the planner, and repeats only while status is pending. A certified metadata run then invokes `ingestion.aws_handlers.inventory_handler` before success. Partial and blocked states fail the execution with distinct error names. Lambda infrastructure is described in Terraform but has not been applied. All three handlers require `APP_ENVIRONMENT` and `RESOURCE_CONFIG_PATH`; local runs use `CONTROL_DATABASE_URL` and optional `AWS_ENDPOINT_URL`, while AWS runs fetch a JSON secret containing `dsn` from `CONTROL_DATABASE_SECRET_ARN`. Scope inputs, configuration, and inventory remain version checked. The state machine definition has only been structurally tested locally, not validated by or deployed to AWS. The Lambda planner and inventory publisher must be load tested against real project sizes before use beyond a bounded pilot; larger workloads may require Fargate.

`infra/orchestration/` now contains the reviewable Terraform foundation for the three Lambda functions, Step Functions, Scheduler group and execution role, shared delivery DLQ, and logs. `Dockerfile.lambda` packages the same Python code with a reviewed AWS resource file. The Terraform ASL template is tested for parity with the Python generator. The image, VPC, database, secret, and versioned object prefixes are inputs; the module does not create or deploy them. See `infra/orchestration/README.md` before planning this stack.

`infra/workers/` describes four config-driven SQS work queues with matching DLQs, four ECS Fargate worker services, three optional control services, a certified-event bus, scoped task roles, capped backlog-per-task scaling, and alarms. `Dockerfile.worker` packages approved scripts and a reviewed resource file; `Dockerfile.control` packages the control services without scripts. Worker tasks default to zero and control services default off; no AWS resources have been applied. Workers resolve each job's stored, hash-checked project configuration instead of pinning one project at process startup. The worker can protect itself through the ECS agent while concurrent slots run; the reviewed config flag defaults off, keeping scale-in disabled until an AWS sandbox test. See `infra/workers/README.md` for numeric pilot settings and remaining gates.
