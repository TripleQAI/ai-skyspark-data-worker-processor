# AWS orchestration foundation

This Terraform root config creates three private Lambda functions (planner, status, metadata inventory publisher), their scoped IAM roles, a Step Functions Standard state machine, one Scheduler group and execution role, a shared Scheduler delivery DLQ, bounded CloudWatch log groups, a dashboard, and failure alarms. It does **not** create schedules, worker queues or ECS services, the database, database secrets, or the VPC. The S3/KMS/ECR foundation is in `infra/foundation/`. Do not enable schedules until a bounded pilot has passed the AWS sandbox gate.

## Inputs and trust boundary

- Build `Dockerfile.lambda` from the project root using an approved Python Lambda base image digest, `RESOURCE_CONFIG_FILE` pointing to the reviewed AWS `resources.yaml`, `--platform linux/amd64`, and `--provenance=false`. Push the image to an approved ECR repository and pass its digest-pinned URI as `lambda_image_uri`. The Terraform `resource_config_file` must be the **same reviewed file** packaged at `/var/task/resources.yaml`.
- Pass an existing control secret ARN whose `SecretString` is JSON with a `dsn` key. When metadata targets TimescaleDB, pass `target_database_secret_arn` as well; only the inventory publisher Lambda can read it. Passwords stay out of Terraform variables and image layers. The selected private subnets and security groups must reach the control database, target database when used, S3, and Secrets Manager through approved network paths.
- Scope `config_object_arns`, `inventory_object_arns`, and `metadata_evidence_object_arns` to approved tenant/project prefixes. The planner reads versioned config and inventory; the inventory publisher reads certified metadata evidence and writes inventory objects. The status function has no S3 permission. The certified bucket must have versioning enabled. Supply customer managed KMS key ARNs when those objects or the secret use such keys. Bucket policies and key policies must also allow these roles.
- Use a remote S3 backend with locking and restricted access. This root config intentionally declares the backend without a bucket or key; provide the reviewed backend configuration during `terraform init`. Protect the state even though the module stores only references to secrets.

The YAML `workflow.poll_seconds` and three feed deadlines drive the Terraform ASL template. `tests/unit/test_workflow_infra.py` checks that the template still matches the Python workflow generator. The three functions use separate IAM roles. After a metadata run certifies, the state machine invokes the inventory publisher before succeeding; a publication failure leaves the previous inventory in place. The Scheduler execution role trusts only this schedule group and can start only this state machine or send failed deliveries to this DLQ. New schedules remain disabled until `skyspark-schedules ... reconcile --apply` is called with reviewed bindings.

## Review sequence

1. Review the AWS resource file, image digest, object prefixes, VPC routes, secret and KMS policies, reserved concurrency, and log retention.
2. Run `terraform init -backend-config=<approved-backend-file>`, `terraform fmt -check`, `terraform validate`, and `terraform plan -out=<reviewed-plan-file>` in this folder. Inspect the plan before any apply. The root config creates cloud resources only when an operator applies that plan.
3. Read `state_machine_arn`, `schedule_group_name`, `scheduler_role_arn`, and `scheduler_dlq_arn` from Terraform outputs. Pass them to `skyspark-schedules` for a read-only schedule preview. The first reconciliation creates disabled definitions.
4. In an AWS sandbox, validate the ASL with `ValidateStateMachineDefinition`, invoke bounded test schedules, inspect control coverage and DLQ behavior, and measure planner and inventory-publisher memory and duration. The publisher's 900-second Lambda cap is a pilot bound; larger project snapshots may require Fargate. The deployed planner image, VPC endpoints, IAM and state machine have not been tested by the local Python unit suite.

The state machine logs errors without execution payloads. A `partial` or `blocked` run fails with a distinct Step Functions error, while the PostgreSQL run record retains detailed counts and reasons. The dashboard shows workflow outcomes, Lambda errors, and Scheduler DLQ depth; alarms cover failed workflows, Lambda errors/throttles, and scheduler delivery failures. Notifications need `alarm_sns_topic_arns`. Worker services remain separate long-running queue pollers; this orchestration stack does not start one Fargate task per SQS message.

For local review, run `terraform init -backend=false`, `terraform fmt -check`, `terraform validate`, and `terraform test`. Mocked plans verify that only the inventory publisher receives the optional target secret and that failure visibility is present. `tests/integration/test_phase9_localstack_scheduling.py` creates a disposable versioned S3 object, executes a Standard state machine, and registers three disabled Scheduler definitions. This does not prove a deployed Lambda, Fargate worker, network route, or real Scheduler delivery.
