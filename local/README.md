# Local control and service baseline

The local harness runs PostgreSQL, TimescaleDB, LocalStack, and a bounded synthetic source fixture in Docker. LocalStack is an AWS API emulator at `localhost:4566`, not a web preview. The planner, dispatcher, publisher, recovery service, and metadata worker are separate containers in the optional `pipeline` profile. No real AWS S3 bucket is required.

## Synthetic metadata pipeline

The optional `pipeline` Compose profile runs a one-shot metadata planner, dispatcher, publisher, recovery service, and one metadata worker against the local databases and LocalStack. The `skyspark-fixture` container serves synthetic equipment, points, wide history, and equipment-scoped rule grids from `local/fixture/data.json` under `/api/{site_uri}/fixtures/{operation}`. It enforces site, ID, batch, request-size, and response-row bounds. This is a **contract-shaped JSON fixture**, not a Haystack wire-protocol emulator. `local/manifests/contract-metadata.yaml` pins the reviewed `local/scripts/contract_metadata.py`; it reads the fixture's explicit snapshot/page receipts and writes normalized equipment and points with raw and target S3 evidence. Recalculate the manifest digest after reviewing any script edit. The older `synthetic-metadata.yaml` remains available for Phase 2–3 fixture tests.

1. Copy `local/.env.example` to `local/.env`. Set the LocalStack token, the two local database passwords, and `PYTHON_BASE_IMAGE` to a reviewed Python image reference pinned by digest. URL-encode reserved characters in database passwords because Compose inserts them into PostgreSQL URLs.
2. From the project root, start the base services with `docker compose --env-file local/.env -f local/compose.yaml up -d`. Apply both migrations with `skyspark-control migrate --migrations migrations/control` and `skyspark-control migrate-target --migrations migrations/target`, using host `CONTROL_DATABASE_URL` and `TARGET_DATABASE_URL`. These host URLs use ports 15432 and 15433.
3. Set `LOCALSTACK_ENDPOINT_URL=http://localhost:4566` and `LOCAL_RESOURCE_CONFIG=local/resources.yaml`, then run `python local/bootstrap.py` from the project root with the package installed. This creates the local queues, buckets, and publication bus.
4. On a fresh local control database, build and start the profile with `docker compose --env-file local/.env -f local/compose.yaml --profile pipeline up -d --build dispatcher publisher recovery metadata-worker`. Keep these services stopped when running the Phase 2 gate against a disposable database.
5. Plan a distinct metadata run with `docker compose --env-file local/.env -f local/compose.yaml --profile pipeline run --rm planner`. Set `PLANNER_SCHEDULED_AT` in the planner container to repeat a specific run; without it the one-shot planner uses the current UTC time.
6. Read `docker compose --env-file local/.env -f local/compose.yaml --profile pipeline logs dispatcher metadata-worker publisher` and inspect the planner's run ID and config hash with `skyspark-control run-status`. The two site jobs contain three equipment and three points across the fixture, with raw and target S3 evidence. Publication delivery means EventBridge accepted the job events; no downstream consumer is installed.
7. After both jobs certify, run `skyspark-control publish-metadata-inventory --run-id <run-id> --tenant-id demo-tenant --project-id demo-project --config-hash <config-hash> --environment local --resources local/resources.yaml` with `CONTROL_DATABASE_URL`, `AWS_ENDPOINT_URL=http://127.0.0.1:4566`, and LocalStack test credentials set. This writes a versioned planning snapshot and records its PostgreSQL receipt. The local bootstrap enables versioning on the certified bucket. The AWS Step Functions definition invokes the same publisher automatically for a certified metadata run; the local Compose profile does not run Step Functions.

The control services start only after migrations and bootstrap. The worker runs the reviewed script as an isolated subprocess and reads its pinned configuration from the control database. The optional Compose pipeline starts a metadata worker; reviewed local fixture scripts for history and rules are exercised by isolated integration tests. The source fixture's `synthetic` tag and stable snapshot hash distinguish its receipts from live SkySpark. Live `readAll` grids observed in Phase 0 lacked complete snapshot/page receipts, so production readers fail closed until the data provider establishes that contract.

After bootstrap, set `TEST_LOCALSTACK_ENDPOINT_URL=http://localhost:4566` and run `python -m pytest -q tests/integration/test_localstack_synthetic_metadata.py` to check actual S3 conditional writes, manifests, checksums, and cleanup. This test skips when the endpoint variable is unset.

For the restart and crash-recovery gate, use an empty disposable control database and stop any continuously running dispatcher or worker. With `CONTROL_DATABASE_URL` set to that database and `LOCALSTACK_ENDPOINT_URL=http://127.0.0.1:4566`, run `python local/phase2_gate.py prepare`. Restart the `control-db`, `timescale-db`, `localstack`, and `skyspark-fixture` containers **without removing their volumes**, then run `python local/phase2_gate.py verify`. The first command commits one two-site metadata plan and an S3 marker without sending SQS. The second proves both jobs and their outbox intents survived, replanning made zero duplicate jobs, the S3 marker survived, and the dispatcher delivered exactly two small job references. `--db-only` checks the PostgreSQL portion when LocalStack is unavailable. The ignored `local/state/` file contains only test IDs and is removed after successful verification.

For the Phase 3 resilience gate, set `TEST_CONTROL_DSN` to an empty disposable control database and `TEST_LOCALSTACK_ENDPOINT_URL=http://127.0.0.1:4566`, then run `python -m pytest -q tests/integration/test_phase3_resilience.py`. The tests create and remove their own work/DLQ pairs and S3 objects. They kill a child worker process after raw upload, recover it with a new fence, prove duplicate acknowledgment, exhaust two retries into a DLQ, redrive a checked job reference, and check exact/oversized source-byte limits. A reviewed script can exit with code `65` to signal a nonretryable schema or cap failure; the worker quarantines that job under its live lease and acknowledges the reference. Other nonzero exits retry under the queue's configured redrive policy. Source access pause and source-specific split handling are later feed work.

For the Phase 4 contract gate, set `TEST_CONTROL_DSN` to an empty disposable control database and `TEST_LOCALSTACK_ENDPOINT_URL=http://127.0.0.1:4566`, then run `python -m pytest -q tests/unit/test_metadata_reader.py tests/integration/test_phase4_metadata_inventory.py`. The test creates isolated S3 buckets, validates the reviewed HTTP fixture reader, publishes and pins a two-site inventory, applies configured history exclusions, records adds/changes, and rejects partial or shrinking metadata runs. It removes its own buckets and requires no live SkySpark credential.

For the Phase 5 local history gate, set `TEST_CONTROL_DSN` and `TEST_TARGET_DSN` to empty disposable databases, `TEST_LOCALSTACK_ENDPOINT_URL=http://127.0.0.1:4566`, and run `python -m pytest -q tests/unit/test_history_reader.py tests/integration/test_phase5_history_splits.py tests/integration/test_phase5_history_pipeline.py tests/integration/test_timescale.py`. The reviewed subprocess test needs an isolated Python environment with this package installed because the runner uses `python -I`; set `TEST_SCRIPT_PYTHON` to that interpreter if it differs from the test interpreter. The tests create/remove their own S3 bucket and do not consume the shared `history_live` queue. `local/manifests/contract-history.yaml` pins the reviewed fixture script. Configure `history_source_lag_minutes` and `history_lookback_windows` in a reviewed binding before using overlap; defaults are zero. The local storage policy appends distinct corrections to `history_observation_revisions` while retaining the first base row. Live SkySpark history still requires provider-complete query receipts before certification.

For the Phase 6 local rules gate, set `TEST_CONTROL_DSN` to an empty disposable database and `TEST_LOCALSTACK_ENDPOINT_URL=http://127.0.0.1:4566`, then run `python -m pytest -q tests/unit/test_rules_reader.py tests/unit/test_scheduled_planner.py tests/integration/test_phase6_rules_pipeline.py tests/integration/test_phase6_rule_checkpoints.py`. Set `TEST_SCRIPT_PYTHON` to an isolated interpreter with the package installed for the reviewed subprocess. The tests create/remove their own S3 bucket and do not consume the shared queues. `local/manifests/contract-rules.yaml` pins `local/scripts/contract_rules.py`; update its digest after a reviewed script edit. `config/bindings/example-local.yaml` selects UTC, a zero-minute settlement delay, and two prior days of overlap for the synthetic fixture. A live project reporting `tz: Chicago` needs its own reviewed IANA source timezone and allowed source tag, and the daily AWS schedule must occur after the source-local day closes and the settlement delay. Every requested equipment ID must appear in a complete receipt even when no detections exist; the live SkySpark grid currently lacks this receipt.

For the Phase 7 local gate, set `TEST_CONTROL_DSN` and `TEST_TARGET_DSN` to separate empty disposable databases, `TEST_LOCALSTACK_ENDPOINT_URL=http://127.0.0.1:4566`, and `TEST_SCRIPT_PYTHON` to an isolated interpreter with this package installed. Run `python -m pytest -q tests/integration/test_phase7_targets.py tests/integration/test_phase7_recovery.py tests/integration/test_phase7_replay.py tests/integration/test_phase7_eventbridge.py tests/unit/test_storage_operations.py`. These tests use isolated S3 buckets and an EventBridge bus and never consume shared SQS queues. `local/manifests/contract-phase7.yaml` pins all three fixture scripts for either S3 or TimescaleDB; `TARGET_DATABASE_URL` is required only when a selected feed targets TimescaleDB. The target migrations add metadata and rule revision/batch tables. The recovery test exits a child process after its rules sink commit, then verifies idempotent retry and one control certification.

For the Phase 8 script gate, run `python -m pytest -q tests/unit/test_phase8_scripts.py tests/integration/test_phase8_standalone_audit.py` with `TEST_CONTROL_DSN` set to a **disposable** migrated control database. The integration test persists five standalone run outcomes and checks their audit records. A utility is registered under `utilities` in a reviewed plugin manifest with `id`, `accepted_context_schema: utility-context-v1`, allowed `targets`, and a digest-pinned `execution` using `context_transport: file` and `output_contract: utility-result-v1`. Supply a `UtilityContext` JSON file containing a canonical UUID `run_id`, registered `script_id`, resolved `config_hash`, target, and bounded scalar parameters. After applying control migrations, invoke `skyspark-standalone-script --profile <path> --binding <path> --manifest <path> --environment local --script-root <path> --context <path>` with `CONTROL_DATABASE_URL` set in the environment. Only reviewed script IDs run; an arbitrary path in the context is not executable. A utility run cannot certify ingestion data. The reviewed subprocess inherits the worker's OS identity, so separate task identity and memory/CPU isolation are Phase 9 deployment work.

For the Phase 9 local infrastructure gate, initialize each of `infra/foundation`, `infra/workers`, and `infra/orchestration` with `terraform init -backend=false`, then run `terraform fmt -check`, `terraform validate`, and `terraform test`. The seven mocked plan checks require no AWS account and test bucket/image counts, optional private endpoints, initial zero workers, tenant/project S3 boundaries, optional target secret IAM, and operational visibility. Set `TEST_LOCALSTACK_ENDPOINT_URL=http://127.0.0.1:4566` and run `python -m pytest -q tests/integration/test_phase9_localstack_scheduling.py` for a disposable versioned config object, Standard state machine run, and three disabled schedules. That test does not consume shared worker queues. No AWS resources are applied or schedules enabled by these local checks.

`skyspark-control request-replay --environment local --resources local/resources.yaml --request-file <approved-request.json>` loads a stored config and exact certified inventory version, verifies the explicit history window or source-local rules day, and atomically records the audit, jobs, and `backfill` dispatch intents. The JSON request needs `request_id` (UUID), `tenant_id`, `project_id`, `config_hash`, `feed`, `inventory_version`, `window_start`, `window_end`, `requested_at`, `requested_by`, `approval_ref`, and `reason`; it contains no credential. A separate privileged operator must first insert an unexpired `ingestion.replay_approval_grants` row for that exact config, inventory version, feed, window, and job cap. The requester cannot create this grant through the replay command. Repeat the same request ID and body to get the same run. The CLI uses `CONTROL_DATABASE_URL`, `AWS_ENDPOINT_URL`, and local test AWS credentials; the separate backfill worker reads its own queue, uses `backfill.job_slots_per_task`, and can acquire no more than `backfill.max_source_calls_per_project` of the shared project permits. Production database/IAM grants must restrict who can insert approval rows and invoke replay.

`skyspark-control measure-storage --environment local --resources local/resources.yaml` reads capped current-object counts and bytes from raw, certified, and inventory prefixes plus control/target relation estimates and history hypertable bytes. It requires both database URLs and the local AWS endpoint. Pricing is not embedded. `skyspark-control retention-preview --resources <reviewed-resources.yaml>` renders lifecycle rules only when an explicit `retention` block has been reviewed. It does not apply S3 expiration or delete table data. Choose retention and table aging after measuring object growth, replay horizon, and how long physical certification evidence must remain available.

For the PostgreSQL control slice alone, start `control-db` with Docker Compose and set `CONTROL_DATABASE_URL` in the shell. Then run these commands from the project root after installing the package:

```powershell
skyspark-control migrate --migrations migrations/control
skyspark-control migrate-target --migrations migrations/target
skyspark-control persist-plan --profile config/profiles/default.yaml --binding config/bindings/example-local.yaml --manifest config/manifests/plugins.yaml --environment local --resources local/resources.yaml --feed history --scheduled-at 2026-09-26T10:05:00Z --inventory local/fixtures/inventory.json --window-start 2026-09-26T10:00:00Z --window-end 2026-09-26T10:05:00Z
skyspark-control seed-checkpoint --profile config/profiles/default.yaml --binding config/bindings/example-local.yaml --manifest config/manifests/plugins.yaml --environment local --feed history --site-ref site-a --start-at 2026-09-26T10:00:00Z
skyspark-control seed-checkpoint --profile config/profiles/default.yaml --binding config/bindings/example-local.yaml --manifest config/manifests/plugins.yaml --environment local --feed history --site-ref site-b --start-at 2026-09-26T10:00:00Z
skyspark-control reconcile-run --run-id <run-id-from-persist-plan>
skyspark-control publish-once --resources local/resources.yaml --owner local-publisher-1
skyspark-control recover-stale --resources local/resources.yaml --run-id <run-id-to-recover>
skyspark-control dispatch-once --resources local/resources.yaml --owner local-dispatcher-1
```

The control database URL must be supplied through `CONTROL_DATABASE_URL`; `migrate-target` also requires `TARGET_DATABASE_URL` for the separate TimescaleDB container. Keep both out of committed files. `persist-plan` writes a run, jobs, and dispatch intents in one transaction. Repeating it with the same inputs creates no extra jobs. After LocalStack queues are bootstrapped, set `AWS_ENDPOINT_URL` to the local endpoint, provide local test AWS credentials, and run `skyspark-control dispatch-once --resources local/resources.yaml --owner local-dispatcher-1` to send a bounded batch of small job references. Dispatch policy, queue routes, and storage caps come from `resources.yaml`.

Seed each approved history/rules site/feed with its reviewed first window start before workers run. Seeding is idempotent for the same start and rejects a changed start; use a separate replay process for historical corrections. The final partition's worker certification advances a contiguous cursor and writes pending publication intents in the same control transaction. Metadata site snapshots create intents without a cursor. Run `reconcile-run` during recovery, especially when jobs certified before seeding or before an earlier window completed. It returns `advanced`, `already_advanced`, `waiting_for_certification`, `unseeded`, `waiting_for_prior_window`, or `superseded_or_overlapping` per site; exit code 2 means some sites still need attention. The sample commands are illustrative and need certified jobs before they can advance or publish.

`publish-once` uses the configured EventBridge bus, source, event type, batch limit, lease, and retry policy. Bootstrap creates the local bus. The publisher verifies the bus before claiming any outbox records, accepts per-entry results, and retries failed entries. `delivered` records EventBridge acceptance only. Consumers must deduplicate by the stable `publication_id`; no downstream consumer is configured yet. The Phase 2 restart gate checks S3 and SQS; EventBridge delivery remains a later integration check.

Inspect an existing equipment/point CSV pair without using the control database:

```powershell
skyspark-control inspect-metadata-export --equipment <equipment.csv> --points <points.csv> --resources local/resources.yaml --project-key <fsk> --site-ref <expected-source-siteRef> [--site-ref <another-source-siteRef>]
```

Supply expected source `siteRef` values from the reviewed site registry. The command returns JSON counts, bounded issue examples, and source file hashes. Exit code 2 means the export has exceptions. Even exit code 0 is only a clean CSV assessment; source-query completeness receipts are required before an inventory can be certified for history or rules planning.

`recover-stale` returns JSON entries moved back to pending dispatch. Its thresholds and per-job redrive cap are in `resources.yaml`; choose the never-started delay from actual SQS retention and measured backlog, not from this local example alone. It does not reset a certified job or a handled failure. Run `dispatch-once` after recovery to send the references. A job at the redrive cap needs operator review; SQS DLQ handling is a separate path.

The LocalStack port is an AWS API endpoint, not a web preview. The Scheduler emulator does not fire schedule targets; later local integration tests will invoke the Step Functions execution directly. Use a separate AWS sandbox for real Scheduler-to-Fargate verification.

Preview the three schedule definitions without contacting AWS or PostgreSQL. The following ARNs and S3 URI are **illustrative only**; no such local state machine, role, DLQ, or versioned config object is provisioned by Compose:

```powershell
skyspark-schedules --profile config/profiles/default.yaml --binding config/bindings/example-local.yaml --manifest config/manifests/plugins.yaml --environment local --config-ref 's3://reviewed-configs/demo/config.yaml?versionId=v1' --group-name ingestion --state-machine-arn arn:aws:states:us-east-1:123456789012:stateMachine:planner --role-arn arn:aws:iam::123456789012:role/scheduler-planner --dead-letter-arn arn:aws:sqs:us-east-1:123456789012:scheduler_dlq --region us-east-1 preview
```

The same arguments with `reconcile` perform read-only AWS/LocalStack drift inspection. `reconcile --apply` creates missing schedules or updates project-owned definitions. They are initially disabled, and real provisioned target resources are required before `--enable` is appropriate. No Scheduler-to-Step-Functions delivery is asserted by a LocalStack definition check.

The scheduled config loader expects one JSON object containing `schema_version`, `profile`, `binding`, and `manifest`, uploaded to a versioned S3 bucket. `config_ref` must include a non-null `versionId`. `local/resources.yaml` caps the downloaded bundle at `config_artifacts.max_bundle_bytes`; the loader checks the returned S3 version and computes the same config hash as the reviewed local files. No such versioned bundle is created by `local/bootstrap.py` yet.

`skyspark-control persist-scheduled --environment local --resources local/resources.yaml --trigger-file <scheduler-input.json>` is the planner entrypoint once that bundle exists. It uses `CONTROL_DATABASE_URL` and `AWS_ENDPOINT_URL`; the trigger can instead come from `SCHEDULED_TRIGGER_JSON`. For history or rules, a certified metadata inventory receipt must already exist in PostgreSQL and point to a bounded, exact-version S3 snapshot. The local bootstrap and sample CSV files do not create such a receipt. `persist-scheduled` will fail rather than plan from `local/fixtures/inventory.json`.

Inspect durable run coverage after planning with `skyspark-control run-status --run-id <run-id> --tenant-id <tenant> --project-id <project> --config-hash <hash> --feed <history|rules|metadata> --resources local/resources.yaml`. `CONTROL_DATABASE_URL` is required. The JSON result counts root and child jobs with certification evidence, expected and completed sites, terminal jobs, and the configured deadline. This command is read-only and does not dispatch or certify work.

Render the Step Functions Standard definition locally with `skyspark-workflow --resources local/resources.yaml --planner-arn <planner-lambda-arn> --status-arn <status-lambda-arn>`. The output is ASL JSON; the command does not create or validate an AWS state machine. A real Step Functions execution invokes `ingestion.aws_handlers.plan_handler` and then repeatedly invokes `ingestion.aws_handlers.status_handler` until certified, partial, or blocked. Both Lambda handlers need `APP_ENVIRONMENT=aws`, `RESOURCE_CONFIG_PATH` pointing to the packaged resource YAML, and `CONTROL_DATABASE_SECRET_ARN` containing a JSON secret with a `dsn` key. For a local direct handler test, use `APP_ENVIRONMENT=local`, `RESOURCE_CONFIG_PATH=local/resources.yaml`, `CONTROL_DATABASE_URL`, and `AWS_ENDPOINT_URL`. The handler code does not configure a public FastAPI endpoint. LocalStack Scheduler does not fire its targets in this baseline, and no Step Functions or Lambda resources are bootstrapped yet.

`Dockerfile.worker` requires a `PYTHON_BASE_IMAGE` build argument naming an approved, pinned image digest, a reviewed `RESOURCE_CONFIG_FILE`, and an approved `SCRIPT_ROOT_DIR`. The worker command takes `--environment`, `--resources`, `--script-root`, and `--queue-class`; it resolves each job's profile, binding, and manifest from the control database. `--worker-id` is optional and otherwise generated per process. The default manifest intentionally has no executable scripts while the live source contract is unresolved. Source-call slots and lease timing are configured in the reviewed manifest and `resources.yaml`; PostgreSQL enforces capacity across worker processes. The synthetic metadata path passed a container-to-LocalStack run; production history and rules scripts remain.

The local `worker.scale_in_protection.enabled` flag is false. For an AWS pilot, set it true only in the reviewed AWS resource bundle packaged into the worker image and supplied to Terraform. The worker then requires `ECS_AGENT_URI` from ECS and fails before receiving SQS messages if it cannot protect its task. Expiry, refresh cadence, and HTTP timeout come from the same resource file. Local unit tests simulate the agent endpoint; an AWS sandbox must prove real task protection and scale-in behavior.

After migrations and `bootstrap.py`, run these commands in separate terminals to exercise the three control roles with local endpoints. Each terminal needs `CONTROL_DATABASE_URL`, `AWS_ENDPOINT_URL=http://localhost:4566`, and LocalStack test AWS credentials. Press Ctrl+C to stop. The dispatcher and publisher use process-generated claim owners unless `--owner` is supplied.

```powershell
skyspark-control dispatch-service --environment local --resources local/resources.yaml
skyspark-control publication-service --environment local --resources local/resources.yaml
skyspark-control recovery-service --environment local --resources local/resources.yaml
```

`dispatch-service` groups references by queue and sends up to ten per SQS request, recording or retrying each entry separately. `publication-service` sends EventBridge batches of up to ten only after the site completion gate. `recovery-service` reopens eligible stale jobs according to `recovery` thresholds. The `control_loop` section sets each idle poll interval. The one-shot dispatcher sent two references to LocalStack SQS, and the metadata worker certified both jobs. Continuous-loop behavior still needs an extended soak test. For AWS, `Dockerfile.control` packages the same commands and `infra/workers/` defines optional Fargate services; no cloud resources have been applied.

When LocalStack is running, set `TEST_LOCALSTACK_ENDPOINT_URL=http://localhost:4566` and run `python -m pytest -q tests/integration/test_localstack_dispatch.py` from the project root. The test creates and removes its own queue and checks that a real SQS batch carries only job references. It skips when the endpoint variable is absent.
